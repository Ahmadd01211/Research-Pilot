# Versioned embedding search (20 October 2026)

The project page now opens an evidence-search workspace. It reads real capability and index states, polls only while jobs are active, and requires explicit paper selection before a question is sent. Search results show the source text and link to the original reader with checksum and reader version in the URL. Prose and figure captions use exact anchors; table rows open their source page because one cell highlight would misrepresent a whole row. This visible retrieval step helps researchers spot wrong matches before answer generation. The tradeoff is one extra review step and no polished chat response yet.

The first hosted-RAG slice indexes only evidence chunks that passed the reader's current quality rules. An authenticated researcher explicitly requests indexing for one extracted paper with `POST /api/v1/projects/{project_id}/documents/{document_id}/index`. `GET` at that path reports real queued, processing, ready, or failed state and actual completed/total chunk counts. No API key is sent to the browser. The feature is off by default; set `RP_EMBEDDING_ENABLED=true` and `RP_GOOGLE_API_KEY` in the local untracked `.env` to opt in. Google receives the eligible source chunk text only after that explicit request. Confirm provider quota, pricing and data-use terms for the account before enabling it.

`document_indexes` fixes the source checksum, reader and chunker versions, provider, model, dimension and prompt format. Each vector points to an existing `evidence_chunks` record; the original PDF and page anchors stay local. The dispatcher publishes bounded batches of eight to the embedding worker. A database lease and token prevent a late worker from publishing after a retry. The index becomes searchable only after all recorded chunks are embedded. A changed extraction/parser/model requires a new compatible index; dimensions alone do not establish compatibility. Existing vectors are retained for future cleanup policy, so storage will grow.

`POST /api/v1/projects/{project_id}/evidence/search` accepts `{ "question": "...", "document_ids": ["..."], "limit": 8 }`. It verifies project and paper ownership and that every selected index is current and complete, obtains one question vector, rechecks ownership, then ranks only selected indexes by pgvector cosine distance. It returns chunk text, kind, source ID, page number, source metadata and distance. This is evidence retrieval, not an AI-written answer. The response gives the UI enough information to link a result to the original page. A low distance is a ranking signal, not proof that the passage answers the question.

Google Embedding 2 uses distinct recommended text formats for documents and questions. We normalize the returned 768-dimensional vectors and store that format in the index identity. The model and query formatting are currently fixed together. This reduces accidental incompatible-vector mixing; it means a model/prompt upgrade triggers re-indexing. HTTP failures are classified without logging credentials or source text; transient failures retry, and invalid provider shapes stop the job. Five attempts are the current bound. A failed index has no retry UI yet and requires a deliberate recovery path. The provider request itself can still fail or be rate-limited. No OCR or vision interpretation is added by this phase.

Verification: additive migration 0007 applied on the existing app database without deleting volumes or papers; API readiness passed; 113 isolated backend tests passed, including a fake-provider end-to-end database search; Ruff and strict mypy passed. No live provider call was possible without a configured key. The earlier seven-question lexical benchmark remains a baseline, not evidence that the new semantic model performs well.
