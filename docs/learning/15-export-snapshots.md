# Export snapshots and their limits

This phase supports two concrete formats: a CSV of verified reference metadata and a Markdown snapshot of one saved writing draft. Export creation is explicit. The server checks project ownership, rejects an archived project, uses a request UUID for idempotent retries, and stores the exact generated bytes with a SHA-256 hash. A later edit cannot change an earlier download. History lists the latest twenty records per page and each download is owner-scoped.

The CSV uses the standard CSV writer, includes a UTF-8 byte order mark for spreadsheet compatibility, and prefixes cells that could be interpreted as formulas. This changes the display of some legitimate leading symbols, a deliberate tradeoff to reduce spreadsheet formula execution when a researcher opens the file. It contains raw fields, not APA/MLA/Chicago-formatted citations. Markdown preserves plain draft text and citation markers; it is not a DOCX file. The draft revision supplied by the UI must still be current when the snapshot is created.

Each file is limited to 2 MB and a project may hold at most 100 MB of export snapshots. The cap protects the database while export retention and purge are designed. History is not a backup, and the current UI cannot remove an old export. Before public release, we need an export retention policy and cleanup path coordinated with project deletion, as well as tested DOCX and structured spreadsheet exports.

To review: open **Exports** from a project, create a reference CSV, download it, then edit a reference and download the historical export again. Its bytes should be unchanged. Save a writing draft and create a Markdown snapshot; if another tab changes that draft before export, the stale request should be rejected.
