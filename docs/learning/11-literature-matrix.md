# Source-linked literature matrix

The matrix is a user-authored comparison table, not an AI extraction claim. Each row belongs to one project and one uploaded paper. The researcher can fill the research question, method, sample/context, finding, and limitation fields, leaving unknown fields empty. Every nonempty field must cite an eligible evidence chunk from that same paper. The backend checks project ownership, current PDF checksum, reader version, chunker version, and document identity before saving. The response retains the source page, version and metadata for a measured PDF link.

Storage uses a row table plus one cell record per populated field. This makes individual field provenance explicit and allows multiple rows for different findings in the same paper. A JSON blob would be quicker to add but would lose database-level field uniqueness and source foreign keys. Edits mark earlier cells superseded and insert current cells; gaps that cite an earlier cell can still show its original text and flag it for review. A partial unique index allows only one current cell per field in a row. Rows use revisions to reject stale edits; removal hides a row while retaining its source record. Archived projects can read the matrix but cannot edit it. A project is limited to 200 active rows in this slice.

The screen uses an actual HTML table so column labels remain meaningful to assistive technology and dense comparisons. On narrow screens it scrolls horizontally. The editor searches eligible chunks by PDF page and lets a researcher inspect the excerpt and original PDF before writing a note. Extraction can still be incomplete or a note can overstate its cited passage; the link is an audit path, not automatic factual verification.

The next step is a review workflow for conflicting or low-confidence fields and candidate research gaps. Gap findings should cite matrix cells and underlying source passages, show uncertainty, and avoid claiming that absence from an incomplete matrix proves a true literature gap.
